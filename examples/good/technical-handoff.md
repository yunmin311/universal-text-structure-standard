# 文本规范维护交接

当前工程把完整写作解释保存在 `STANDARD.md`，把稳定约束和检测映射保存在 `FORMAT_RULES.yaml`。维护时要同步两者，但不让正文退化为规则表的逐行翻译。采用这种分工，是因为执行者需要理解条件与例外，而轻量检测器只需要稳定字段及可识别的局部模式。

## 工作原理与实际修改

Schema 是规则数据的结构契约，用来拒绝缺少字段、类型错误和不受支持的枚举值。它不能证明自然语言解释正确，也不能仅靠对象去重保证某个字段唯一，因此脚本另行检查规则编号。Markdown 检查器处理围栏、代码跨度、双星号与简单表格，并将不确定的写作意图留给人工判断。

本轮将规范版本与数据结构版本分开：修改写作解释可以提升 `standard_version`，不必同时改变 `schema_version`。字段格式也改为技术实体默认只使用 inline code；语义标签可以加粗，但不因文件名出现于行首就同时强调。这些改变需要正反样本支持，不能只改正文而继续把旧字段语法当作默认正确答案。

- `STANDARD.md`：解释执行条件、模式差异、段落职责与完整检查流程。
- `FORMAT_RULES.yaml`：保存简短约束、稳定编号与双向样本映射。
- **验证入口：** `scripts/validate.py`，分别运行数据检查和测试。

## 如何验证与复用

交接不能把“存在测试文件”写成“测试通过”。接手者应运行下列命令，读取实际退出状态，再把检查对象、结果和限制写入本次工作记录。这里给的是复用方法，不冒充某次运行的结果。

```bash
python scripts/validate.py --schema
python scripts/validate.py --test
```

| 检查 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| Schema 与引用检查 | 数据结构、编号和样本映射符合约束 | 规则文案在所有场景都合理 |
| Fixture 测试 | 已登记输入得到预期诊断 | 检测器支持完整 Markdown |
| 人工审读 | 本次文档的结构与任务相匹配 | 未阅读文档也会自动符合规范 |

失败时先按诊断定位规则或样本，不通过删除预期来消除红灯。若新输入属于合法例外，应先保留它作为回归样本，再缩小检测模式；若是语义分歧，则记录分歧依据，等待确认后修改正式定义。这样后续复用能区分规则改变与检测器修复。

## 接手边界

稳定规则编号不能因为文案重写而更换，自动化 PASS 也不能替代语义复核。私人来源只能保留在被忽略的本地目录，公开样本需要脱敏；旧提交已经保存的信息不会随新提交删除而消失。接手者必须知道这项区别，在获得明确授权前不能改写历史或强推。

下一次维护从实际出现的问题开始：判断它属于已有规则解释不足、检测遗漏，还是一个真正独立的新约束。优先补解释或样本，不为了把每个偏好机器化而增加规则。交付时保留已验证事实、未覆盖语法和需要决定的冲突，避免让下一位 Agent 重新推测当前状态。
